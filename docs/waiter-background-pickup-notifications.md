# BusinessOS Restaurant: background pickup notifications

## What is implemented

When cloud Laravel KOT production changes a ticket item to READY, the tenant transaction writes an idempotent push event for **active devices registered to that order's waiter**. A scheduled job delivers via Firebase Cloud Messaging HTTP v1 (FCM), with APNs delivery for iOS and OS notification delivery for Android. Token registration is authenticated by both the waiter Sanctum token and the existing central device secret. Tokens are encrypted in the tenant database. Messages include only the table/service label and opaque order/item IDs; never price, customer phone, token or credential.

The waiter app requests notification permission, registers/rotates its FCM token using the **cloud** endpoint, and deep-links a tapped notification to the synced order. Signing out unregisters and deletes the FCM token. The foreground pickup list and LAN-first sync continue to work without FCM.

## External setup REQUIRED before a real background push can arrive

1. Create a Firebase project in the Firebase Console. Register the Android package and iOS bundle identifier generated by `flutter create --org af.businessos --project-name businessos_restaurant_waiter` (check final `applicationId` and `PRODUCT_BUNDLE_IDENTIFIER` in the generated projects).
2. Enable Firebase Cloud Messaging API. In Firebase Project Settings, obtain **public app configuration** for Android and iOS. Add these five GitHub **Actions repository variables** (not secrets): `RESTAURANT_FIREBASE_API_KEY`, `RESTAURANT_FIREBASE_ANDROID_APP_ID`, `RESTAURANT_FIREBASE_IOS_APP_ID`, `RESTAURANT_FIREBASE_SENDER_ID`, `RESTAURANT_FIREBASE_PROJECT_ID`. The release workflow inserts them as Dart defines. Builds without them still work, but push enrollment stays disabled.
3. For the production Laravel server, securely create a **service account JSON file outside the web root**, readable only by the app service user (not in git or GitHub artifact). Add server env `RESTAURANT_FCM_CREDENTIALS=/secure/path/service-account.json` and `RESTAURANT_FCM_PROJECT_ID=actual-project-id`. Use `php artisan config:cache` only after ensuring env is correct. Never place this private service credential in a mobile app.
4. Deploy the matching Laravel release to each tenant host, run **tenant migrations**, and configure a cron to run Laravel scheduler once per minute:
   `* * * * * cd /path/to/restaurant && php artisan schedule:run >> /dev/null 2>&1`
   The scheduler includes `restaurant:deliver-ready-push`. Check cron logs; the worker retries transient failures and expires stale events after two hours.
5. **iOS additionally requires paid Apple Developer membership**, an APNs authentication key uploaded into Firebase, an Apple-signed build with Push Notifications capability and Background Modes → Remote Notifications enabled. The unsigned CI IPA cannot receive APNs on a physical device as-is. Native Firebase method swizzling must stay enabled. Create a signed/TestFlight or provisioned install with correct entitlements. This repo's unsigned runner configures the Info.plist background mode but **does not** provision APNs signing.
6. Test with an actual Android device with Google Play services and a physical, properly signed iPhone. Grant permission and log in as the waiter assigned to the order. With the app closed/suspended, mark the KOT item READY on the **cloud-integrated** kitchen. Verify delivery, correct table, tapped order navigation, and no duplicates on retries.

## Boundaries / safety

- FCM requires external Google/Apple push infrastructure, phone internet connectivity and permission. **Pure offline-LAN kitchen state is not automatically forwarded to the cloud**; background push cannot arrive while the cloud has not received READY. The existing in-app LAN pickup banner remains the fallback while app is running.
- Foreground alerts may arrive via local sync without external services. FCM delivery depends on OS and network; no promise of 100% immediate delivery.
- Device enrollment is per authenticated user and activated device. Queue rows are idempotent, tied to the actual READY item, and rechecked against current waiter assignment and READY status before sending. Cancelled/served/voided/expired events are dropped.
- Rotating credentials must update the cloud server and (for client app IDs) rebuild a new app. If FCM is not configured the worker deliberately preserves queued events, without publishing misleading success.
- Token contents and server secrets must not appear in logs. Use a restricted outbound firewall allowlist to Google OAuth/FCM API hosts. See [Firebase FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api) and [FCM Flutter setup](https://firebase.google.com/docs/cloud-messaging/flutter/get-started).
